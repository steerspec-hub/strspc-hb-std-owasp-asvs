# OWASP ASVS 5.0.0 as a SteerSpec Standard Realm

This repo holds the realm `dev.steerspec.std.owasp.asvs.v5`, a transcription of the
[OWASP Application Security Verification Standard](https://github.com/OWASP/ASVS) 5.0.0.

A project that depends on it can be measured against the **whole** standard, at a chosen level, rather
than only against the clauses it happened to map.

> This is SteerSpec's transcription, not an OWASP publication. The standard's text is OWASP's.
> Report a transcription error here. Report an issue with the standard itself to
> [OWASP/ASVS](https://github.com/OWASP/ASVS).

## Status

All 345 requirements of ASVS 5.0.0 are transcribed as 503 Published rules: 70 clauses at L1, 253 at
L2 and 345 at L3. Before they were Published, they were checked against OWASP's release: the vendored
source is byte-identical to the release asset, and for every requirement of both the flat JSON and
the CSV export, its rules joined in order give the requirement's text, with matching clause, levels,
chapter and section. Next:

- [#2](https://github.com/steerspec-hub/strspc-hb-std-owasp-asvs/issues/2): the crosswalk from
  4.0.3 to 5.0.0.

## Layout

The realm follows the core Standard Realm rules (STDRLM) of `dev.steerspec.core`:

- `rules/realm.json` declares `"kind": "standard"`, the edition, the licence, the attribution and the
  profiles `L1`, `L2` and `L3`.
- Each chapter is an entity (`V01`) and each section a sub-entity (`V01S01`), zero-padded because an
  entity ID has 3 to 18 characters. Requirement `V1.1.1` becomes rule `V01S01-001`.
- Each requirement becomes one or more rules, in the standard's order. A requirement with more than one
  sentence becomes one rule per sentence. Every rule carries the standard's number in `clause` (for
  example `V1.1.1`) and its levels in `profiles`.
- The rules are generated by [`tools/generate.py`](tools/generate.py) from OWASP's
  `OWASP_Application_Security_Verification_Standard_5.0.0_en.flat.json` (release `v5.0.0_release`),
  kept in [`source/`](source/), with `strspc realm add`, `strspc entity add` and `strspc rule add`. No
  rule JSON is written by hand. Only Markdown escapes of punctuation are removed (`Sec-Fetch-\\*`
  reads `Sec-Fetch-*`).
- The rules are Published, so they are never regenerated: rule IDs are never reused. A fix is
  `strspc rule supersede`, and when the new rule is Published, `strspc rule terminate` moves the old
  one to Terminated in the same change (STDRLM-013). The generator stays as the record of how the
  rules were made, and for a later edition.
- The rules are never Implemented: a standard is measured against, not evaluated against code
  (STDRLM-010).
- CI lints in strict mode. The bodies are the standard's own wording, so a Rule body may hold no Key
  Word and keep its examples (STDRLM-020, STDRLM-021). strspc 1.41.0 and later skip those two
  checks in a realm of kind standard.

## Using it

In your own `realm.json`, declare the realm as a dependency, and add a Standard Reference that links
to it, with the level you claim:

```json
{
  "realm": {
    "standards": [
      {
        "id": "owasp.asvs",
        "version": "5.0.0",
        "relation": "implements",
        "realm": "dev.steerspec.std.owasp.asvs.v5",
        "profile": "L1"
      }
    ]
  },
  "dependencies": [
    {
      "realm_id": "dev.steerspec.std.owasp.asvs.v5",
      "version": "<release>",
      "source": "github://steerspec-hub/strspc-hb-std-owasp-asvs@v<release>/rules"
    }
  ]
}
```

The rest of your manifest stays as it is; only these two parts change.

Then `strspc standards coverage` reports which clauses your rules cover, which are mapped but not yet
enforced, and which nobody mapped, against the clause total of your level.
